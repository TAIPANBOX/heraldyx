# heraldyx 0.3.0

An event is processed as the source it claims only when the file it was read from may carry that source.

## What changed

- **A line in the wrong file is refused, counted and said once** (#85, bus layer 2,
  the reader half). Until now heraldyx read every line of every file under
  `HERALDYX_EVENTS` and rendered it as the plane its `source` named, so a line
  claiming `wardryx` inside `tokenfuse.ndjson` was mailed as a wardryx event
  about whatever agent it named. Now `<source>.ndjson` carries `<source>` for the
  fourteen registered sources, `tokenfuse-cloud.ndjson` and `tokenfuse-mcp.ndjson`
  carry `tokenfuse`, and `HERALDYX_STREAMS` declares anything else. A refused
  line never leaves the watcher: the rule, the renderer, the fleet picture and
  the digest cannot see it. The count is kept in `Watcher.ForeignSource` and printed
  once per growth.
- **Two new notices, `foreign_source` and `unknown_stream`, one alert each, never a flood.** For each (file, claimed
  source) pair heraldyx raises ONE `high` alert, `foreign_source`, naming the
  file, the claim, how many events and what the file may carry, and nothing the
  refused lines said. A file nobody declared is still read when its lines claim
  its own name, and is raised once as `unknown_stream`; a line in it claiming
  any other source is refused. Both go through the same severity floor, dedup
  window and hourly ceiling as an event (below the floor they land in the
  daily summary), are remembered in the state file so a restart does not mail a
  pair again, and are filed under no agent, so the journal counts the missing
  record and says so. The journal's dispatch `kind` gains the same two names.
- **`HERALDYX_STREAMS`** (the 18th variable, optional): `stem=source|source`,
  comma-separated. It widens what a file may carry and never narrows it. A
  malformed entry refuses startup naming the variable.
- **`demo.ndjson` is opt-in.** It is not built in, because any co-tenant of the
  events directory could create it and speak as six planes. Declare it with
  `HERALDYX_STREAMS=demo=tokenfuse|wardryx|engram|qryx|verdryx|mockryx`.
- **typryx's four event types are described** (#83): `typed_answer`,
  `typed_unanswered`, `typed_refused` (worded per refusal reason) and
  `calibration_drift`, so the catalog is 46 types. Five more `data` keys are
  allowlisted (`template`, `template_version`, `backend`, `model`,
  `bounds_crossed`), each a configuration identifier or a measured number.
- **Dependency and CI** (#84): `github/codeql-action/upload-sarif` 4.38.0 to
  4.38.2 in the Scorecard workflow, still pinned to a commit.

## Upgrade note

0.2.5 to 0.3.0 is a minor release with one behaviour change an operator can
notice, and it is the point of the release.

- If a producer writes a file whose name stem differs from the `source` its
  lines claim, those lines are refused as of 0.3.0, and one `foreign_source`
  alert says so. Either name the file for its source (`tokenfuse.ndjson`) or
  declare it: `HERALDYX_STREAMS=events=tokenfuse|wardryx`. The old README recipe
  that wrote `source: tokenfuse` lines into `events.ndjson` is exactly this case.
- `demo.ndjson` is no longer read as six planes. If you run a demo against
  heraldyx, set the `HERALDYX_STREAMS` declaration above in its environment.
  `taipan demo` starts no heraldyx today, so nothing in the estate needs it set.
- No variable was removed or renamed, and the state file gains a `raised` key
  that an older file simply lacks. A deployment that points `HERALDYX_EVENTS` at
  the launchers' own directory needs no change: the file names the table
  assumes were read from the launchers' code, so check the first start's log
  for a `watch: ... refused ...` or `no declaration for ...` line.
- Launchers pin `v0.2.5` until they move; no deployment carries the rule before
  that.

## Evidence and limit

234 test functions (179 at 0.2.5); 46 event types; 38 Gherkin scenarios in five
files, each bound to a named test both ways by `scripts/features-are-bound.sh`
(`features/source-must-match-its-stream.feature` has 14); 22 teeth cases in
`scripts/gates-have-teeth.sh`. #85's twelve behavioural tests were run against
the unfixed tree first (ten red on behaviour, two guard against over-blocking
and are held by mutants), and nine mutants of the fix were each caught by a
named test. The real binary over one bus directory mailed `run-forged` before
and not after.

## Not proven

- A live box with a hostile co-tenant: the runs used a directory written by
  hand and file delivery, never SMTP.
- A process that creates `wardryx.ndjson` before wardryx does and writes
  `source: wardryx` into it passes, because the name and the claim agree.
  Directory ownership in the launchers and a per-file owner-uid check would
  close that, and neither is built.
- A writer compromised in its own uid can still forge its own stream; only
  signing closes that.
- The exception table is a copy that heraldyx and Idryx each carry; nothing
  holds the two equal.
- The launchers writing the file names the table assumes is a reading of their
  code, not a run. idryx, qryx and engram have no launcher-configured file;
  their names are the convention, not a measurement.
- From #83: a live `typed_unanswered` from a real backend failure, a live
  `typed_refused` for each backend reason, and a burst of refusals under a real
  fleet were not measured. SMTP delivery of any of the new mails was not
  measured either.
