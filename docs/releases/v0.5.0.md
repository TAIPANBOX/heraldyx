# heraldyx 0.5.0

A second TokenFuse gateway can now reach the mail. That gateway runs on the
OpenAI wire (`TOKENFUSE_WIRE=openai`) and writes its own stream file,
`tokenfuse-openai.ndjson`. Before this release that file was not in the table
of files that may carry the `tokenfuse` source, so every line in it was refused
as a foreign source and nothing from that gateway was mailed. Its lines are now
processed as TokenFuse events, under the same severity floor, dedup window and
hourly ceiling as any other.

The file name is the rule. A gateway that writes its stream under another name
is still refused until the file is renamed or declared in `HERALDYX_STREAMS`,
as before.

## What changed

- **The second TokenFuse gateway's file is read as TokenFuse** (#99, invariant
  22). `tokenfuse-openai.ndjson` joins `tokenfuse-cloud` and `tokenfuse-mcp` in
  the exception table in `internal/stream`. A TokenFuse line in that file is
  processed as TokenFuse. A line in the same file that claims another plane is
  still refused, counted, and raised once as an alert that names the file and
  the claim. The change has one behavioural test in
  `cmd/heraldyx/source_test.go` and one scenario in
  `features/source-must-match-its-stream.feature`; the README and CLAUDE.md
  name the file.
- **The README diagram and its counts match the code** (#98). Qryx and Idryx
  are drawn as planes that both read and write the log: Qryx appends with
  `qryx --events`, and Idryx has an event sink. The alt text says twelve planes
  write the log, and the data allowlist has 22 keys, not eleven. Docs only.
- **The validation record no longer names the owner** in its 2026-08-02
  mailbox entry (#100). Docs only.
- **README badge and pull line for v0.4.0** (#97), the follow-up the v0.4.0
  tag needed once its image was published. Docs only.

The event-type catalog is unchanged at 50 types.

## Upgrading

- Nothing to configure. No variable was added or removed.
- A deployment that pins v0.4.0 keeps refusing `tokenfuse-openai.ndjson` until
  it moves to v0.5.0.

## Not proven

- No live second gateway has written `tokenfuse-openai.ndjson` into a running
  heraldyx, and no line from it has been mailed through SMTP. The producer side
  was read from TokenFuse 1.11.0's source, not run here.
- The exception table is a copy that heraldyx and Idryx each carry. Both
  received the `tokenfuse-openai` row in this release, in separate pull
  requests; no gate compares the two tables.
- Two events of one type on one run inside the dedup window still produce one
  mail, because the dedup key is the type and the run. Measured, not changed.
- A process that creates `tokenfuse-openai.ndjson` before the gateway does, and
  writes `source: tokenfuse` into it, is read as TokenFuse, because the name and
  the claim agree. Directory ownership in the launchers and a per-file owner-uid
  check would close that, and neither is built.
