# heraldyx 0.7.0

The box now says it is alive once a day, lets an operator acknowledge a condition
they already know about, and can hold alerts for a quiet period every night or for
a maintenance window opened by hand. None of the three holds a `critical`.

## What changed

- **A daily pulse says the notifier is alive (#108).** Once per
  `HERALDYX_PULSE_HOURS` (default 24, `0` turns it off) the box sends one mail with
  the numbers it saw: events read, alerts handed to the mail transport, alerts held
  at the hourly limit, and when the last event was read. When the daily summary goes
  out in the same period it carries the pulse, so a busy day still gets one mail.
  A quiet fleet and a dead notifier no longer look the same, because the absence of
  the pulse is the signal.
- **Acknowledge a condition by its key (#109).** Every alert has a `Key:` line.
  `--ack <key> [--for 4h] [--by <name>] [--note <text>]` holds alerts below critical
  about that key for a bounded time: four hours by default, seven days at most, and
  a longer one is refused. `--unack <key>` ends it at once, and `--acks` lists what
  is in force. When an acknowledgement ends, one mail says how many alerts it held,
  the worst severity among them and when the first was held. A critical about an
  acknowledged key is sent at once, with one line saying it was acknowledged.
- **Quiet hours and maintenance windows (#110).**
  - `HERALDYX_QUIET=HH:MM-HH:MM` holds alerts below critical every day in that
    window. `HERALDYX_TZ` names the IANA zone the hours are read in, for example
    `Europe/London`, and the hours stay on wall time across summer time. A value
    that cannot be read turns quiet hours off, the log says why, and the notifier
    still starts.
  - `--maintenance <duration> --note <text> --by <name>` opens a window by hand.
    `--scope <source>` holds only one source's alerts, for example while only
    tokenfuse is being upgraded. `--maintenance-end` closes the window now. A window
    runs at most 24 hours, and `--maintenance 25h` is refused. Opening a new window
    replaces the one in force.
  - When a window opens, one mail says what it holds and until when. When it closes,
    one mail says how many alerts it held, even when the count is zero, because that
    mail is how an operator learns alerting is back.
- **A critical is never held.** An acknowledgement, the quiet hours and a window all
  leave a `critical` alone. It is sent at once, the dedup window still applies, and a
  critical sent during a window says so in its body.
- **Held alerts do not count toward the hourly ceiling**, because nothing was sent.
  Every event stays in the log and the console.

## New configuration

| variable | default | what it is |
|---|---|---|
| `HERALDYX_PULSE_HOURS` | `24` | how often the box says it is alive, `0` for never |
| `HERALDYX_CONTROL` | `control.json` beside the state file | the control file, holding the acknowledgements and the maintenance window; written only by `--ack`, `--unack`, `--maintenance` and `--maintenance-end`, and read by the running notifier |
| `HERALDYX_QUIET` | empty (off) | daily quiet hours as `HH:MM-HH:MM` |
| `HERALDYX_TZ` | empty (the process's own zone) | the IANA zone `HERALDYX_QUIET` is read in |

No existing variable was renamed or removed. The zone database is compiled into the
binary, so the image needs no tzdata.

## Upgrading

- **The pulse is on by default.** A box that already has recipients starts getting
  one mail every 24 hours after the upgrade. To keep the old silence, set
  `HERALDYX_PULSE_HOURS=0`.
- The acknowledgement and window commands run in the notifier's container, for
  example `docker compose exec heraldyx /usr/local/bin/service --acks`. They write
  `control.json` beside the state file. The running process only reads that file, so
  a command never races the loop's own state.
- `state.json` gains the pulse counters and the window's announcement. The
  acknowledgements and windows are not written to the dispatch journal in this
  version. The pulse is filed under the last agent that caused a message in its
  cycle, or counted as a gap when none did, as the daily summary is.
- Rolling back to 0.6.0 with a 0.7.0 `state.json` was not run for this release.

- 380 test functions, and the README badge says so (`scripts/readme-numbers.sh`).
  100 scenarios in `features/`, each bound to a named test
  (`scripts/features-are-bound.sh`).
- Local gate run on this tree, every gate exit 0: `gofmt -l .`, `go vet ./...`,
  `go test -race -count=1 ./...`, `scripts/one-way-out.sh`,
  `scripts/readme-numbers.sh`, `scripts/features-are-bound.sh` and
  `scripts/gates-have-teeth.sh` (25 cases).
- Statement coverage from `go test -race -count=1 -coverprofile ./...`: 92.3% in
  total; `internal/rule` 92.5%, `internal/render` 95.6%, `internal/config` 93.9%,
  `internal/control` 86.8%, `cmd/heraldyx` 95.1%. Not re-measured against 0.6.0 for
  this note.
- The control commands were run against the built binary in a scratch directory:
  `--acks` on an empty file, `--ack policy_deny:run-1 --for 4h`, `--acks` again,
  `--ack x:y --for 169h` (refused), `--unack`, `--maintenance 25h` (refused),
  `--maintenance 30m --scope tokenfuse`, and `--maintenance-end`. Each printed the
  text this note describes.

## Not proven

- No mail of the three new kinds (the pulse, an acknowledgement's end, a window's
  open and close) was sent through an SMTP server for this release. Their content
  was checked by tests and the file transport only.
- Quiet hours across a change to summer time were not run on a live box.
- Rolling back to 0.6.0 with a 0.7.0 state file was not run.
- The release and image jobs run only on the tag push. The image's signature and
  provenance are proven by that run, not by this branch.
